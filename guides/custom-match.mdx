## Create and join a custom match

Use the band room system to create a private lobby, configure its arena and seats, invite players with a `t`-prefixed room ID, and start an immediately allocated practice match.

## Prerequisites

<Callout kind="info" collapsed="false">
  Before you start, confirm that you have:

  - A running server on port `18080`
  - Worker supervision enabled (`worker.enabled = true` in `server-config.json`)
  - A patched game client
  - An authenticated player account
  - At least two game clients for multiplayer testing
  - An authenticated out-game WebSocket connection using `user_uid` and `connectionToken`
</Callout>

When worker supervision is enabled, the server automatically launches the dedicated game worker.

## How custom matches work

Custom matches use persistent band rooms managed by the server's lobby system. Each room receives an ID beginning with `t`, which identifies it as a team room to the client. The full room ID is the join code.

The accepted `roomType` values are:

- **`squad`**: Standard party room
- **`practice`**: Custom or practice room
- **`none`**: No room type

The server still accepts the legacy numeric ordinals for compatibility, but responses serialize the string slug.

Practice rooms expose ten one-based seats:

- **Seats&#x20;****`1`****&#x20;through \*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*****`6`** have role `player`
- **Seats&#x20;****`7`****&#x20;through \*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*****`10`** have role `spectator`
- **Seats&#x20;****`1`****&#x20;through \*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*****`3`** belong to Team 1
- **Seats&#x20;****`4`****&#x20;through \*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*****`6`** belong to Team 2

The only valid seat role slugs are `player` and `spectator`. The host is determined by the room's `HostUid`, not by a seat role.

Bots fill unused player seats, but never spectator seats or seats disabled by the host. A room with one human normally receives five bots. A room with two humans normally receives four bots in the six-player layout.

<Callout kind="tip" collapsed="false">
  Share the complete `t`-prefixed room ID directly with players who should join. The server does not create a separate invitation code, and rooms do not have password protection.
</Callout>

Every band mutation returns a structured envelope similar to this shape:

```json
{
  "roomId": "t7f3a91c4e2bd",
  "room": {},
  "evt": {
    "roomId": "t7f3a91c4e2bd",
    "_ty": "BandUpdateEvent",
    "seq": 18,
    "commands": []
  },
  "result": {},
  "seq": 18
}
```

The client applies `evt.commands` rather than replacing its local state with the `room` object. Each event contains nine typed command slots: `room_enter`, `room_exit`, `room_transit`, `arena_update`, `seat_update`, `member_update`, `moderator_update`, `bot_update`, and `bot_reset`. A command object includes all slots, but only the slot for that command is non-null.

## Create a custom room

Create a room with `POST /api/v1/band_room/create`. Use snake\_case fields in new requests. Legacy camelCase aliases remain accepted, but the server's current request and response model uses names such as `input_character`, `input_arena`, and `input`.

<Steps>
  <Step title="Choose the room type" title-type="p">
    Set `roomType` to one of the supported string slugs:

    - `squad` for a party room
    - `practice` for a custom or practice room
    - `none` when no room type is selected

    Use `practice` when you need the ten-seat layout with six player seats and four spectator seats.
  </Step>

  <Step title="Select the arena" title-type="p">
    Provide an arena object through `input_arena`. The current arena configuration uses map IDs `4003` through `4010`, rule ID `106`, and internal mode ID `3`.

    A request can use this shape:

    ```json
    {
      "roomId": "",
      "roomType": "practice",
      "input_arena": {
        "input": {
          "arenaSlotId": 1,
          "mapId": 4003,
          "ruleId": 106,
          "fairPlayMode": null
        }
      }
    }
    ```

    The available arena slots and map IDs come from the `arena` section of `server-config.json`. That section also controls `tokenTtlSeconds`, which defaults to `600`, and `competitiveSeasonId`.
  </Step>

  <Step title="Pick a character" title-type="p">
    Provide the creator's character selection through `input_character`. The nested `input` object can include the character ID, character level, skin, emoticons, fashion items, and banned character IDs.

    The server stores the selection as part of the member update emitted in the mutation event.
  </Step>

  <Step title="Create the room" title-type="p">
    Send the create request. The server generates a `t`-prefixed room ID, records your account in `HostUid`, places you in a player seat, and sets the room state to `lobby`.

    The server reconciles bots into free player seats when bot filling is enabled. Disabled seats and spectator seats are excluded from bot fill. Keep the returned room ID because other players use it to join.
  </Step>
</Steps>

A room normally moves through these states:

```text
lobby -> ticket -> battle
```

Custom match tickets are placed immediately, so the ticket normally completes without waiting in the queue. The room model still exposes `battle`, and the server automatically launches a supervised game worker to host the match when the room transitions to this state.

## Share the room ID

The room ID is the working invitation method. Send the complete ID to each player who should join, then have them use the join-by-ID endpoint.

The social invitation endpoints exist at:

```text
POST /api/v1/band_social/invite
POST /api/v1/band_social/reject
```

These endpoints are compatibility stubs. They authenticate and accept requests, but they do not deliver notifications, store invitations, or add players to the room. Share the room ID directly instead.

## Join a custom room

Join a known room by ID or ask the server to find an open room. Include the joining character under `input_character`.

<Steps>
  <Step title="Join by room ID" title-type="p">
    Call `POST /api/v1/band_room/join` with the room ID and character selection.

    ```json
    {
      "roomId": "t7f3a91c4e2bd",
      "input_character": {
        "input": {
          "characterId": 12,
          "characterLevel": 15,
          "skinId": 2,
          "emoticonIds": [],
          "fashionItemIds": [],
          "bannedCharacterIds": []
        }
      }
    }
    ```

    The server looks up the room, assigns an available seat, stores the selected character, and returns the mutation envelope with the updated event commands.
  </Step>

  <Step title="Join an open room when you do not have an ID" title-type="p">
    Call `POST /api/v1/band_room/join_open_room` with the region and character selection:

    ```json
    {
      "region": "global",
      "input_character": {
        "input": {
          "characterId": 12,
          "characterLevel": 15
        }
      }
    }
    ```

    The server joins the first suitable open room whose host is not your account. If no room is available, it returns a `404`-style response with `no open room available`.
  </Step>

  <Step title="Select your character" title-type="p">
    Include a character selection when you join, or update it afterward through `POST /api/v1/band_member/character`.

    Use the current request shape:

    ```json
    {
      "roomId": "t7f3a91c4e2bd",
      "input_character": {
        "input": {
          "characterId": 12,
          "characterLevel": 15
        }
      }
    }
    ```

    Changing your character sets your member state to `select_character`.
  </Step>

  <Step title="Confirm your seat" title-type="p">
    Practice-room seats use one-based `sortKey` values from `1` through `10`. Seats `1` through `6` are player seats, and seats `7` through `10` are spectator seats.

    Player team assignment follows the seat range:

    - Seats `1` through `3` belong to Team 1
    - Seats `4` through `6` belong to Team 2

    Move your member with `POST /api/v1/band_member/move` and `sortKey_dest`. The legacy field `keyDest` remains accepted.
  </Step>
</Steps>

A seat move uses this request shape:

```json
{
  "roomId": "t7f3a91c4e2bd",
  "sortKey_dest": 4
}
```

Moving to an occupied seat displaces the occupant to the mover's previous seat. The server rejects moves outside the practice-room range, into disabled seats, or after the room leaves `lobby`.

You can move a member between rooms with `POST /api/v1/band_room/move`:

```json
{
  "prev_roomId": "t7f3a91c4e2bd",
  "next_roomId": "t1a8d42f0c6be",
  "input_character": {
    "input": {
      "characterId": 12,
      "characterLevel": 15
    }
  }
}
```

## Configure the match as host

Only the account in `HostUid` can change the arena, manage bots, change seat flags, remove members, or transfer ownership. A seat role does not determine host ownership.

Open the current room with `GET /api/v1/band/current` or `GET /api/v1/band/get?roomId=t7f3a91c4e2bd` while configuring it.

<ExpandableGroup>
  <Expandable title="Change the arena" default-open="false">
    Call `POST /api/v1/band_moderator/arena` to update the arena through `input_arena`.

    ```json
    {
      "roomId": "t7f3a91c4e2bd",
      "input_arena": {
        "input": {
          "arenaSlotId": 1,
          "mapId": 4003,
          "ruleId": 106,
          "fairPlayMode": null
        }
      }
    }
    ```

    The updated arena is stored on the room and used for ticket allocation. The mutation event includes an `arena_update` command.
  </Expandable>

  <Expandable title="Modify bots" default-open="false">
    Call `POST /api/v1/band_moderator/bot` to edit one bot:

    ```json
    {
      "roomId": "t7f3a91c4e2bd",
      "botId": "bot_01",
      "input": {
        "characterId": 12,
        "characterLevel": 15,
        "difficulty": "level_2"
      }
    }
    ```

    Valid difficulties are `""`, `nobrain`, `level_1`, `level_2`, and `level_3`. Bots always have a non-null `characterId` and `characterLevel`.

    Single-bot edits emit `bot_update`. Bot fill and reset operations reconcile bots into free player seats and emit `bot_reset`. Spectator seats and persistent disabled seats are never used for bot fill.
  </Expandable>

  <Expandable title="Kick a member" default-open="false">
    Call `POST /api/v1/band_room/kick` to remove a player from the room.

    Only the account in `HostUid` can kick members. The server refreshes the roster and bot fill after the member leaves.
  </Expandable>

  <Expandable title="Delegate ownership" default-open="false">
    Call `POST /api/v1/band_room/delegate` to transfer `HostUid` to another current member.

    Use delegation before leaving when another player should continue managing the room.
  </Expandable>

  <Expandable title="Swap or disable seats" default-open="false">
    Swap members with `POST /api/v1/band_moderator/swap`:

    ```json
    {
      "roomId": "t7f3a91c4e2bd",
      "sortKey_a": 2,
      "sortKey_b": 5
    }
    ```

    The legacy fields `keyA` and `keyB` remain accepted. Swapping uses one-based seat values from `1` through `10`.

    Set one seat's enabled state with `POST /api/v1/band_moderator/seat`:

    ```json
    {
      "roomId": "t7f3a91c4e2bd",
      "sortKey": 10,
      "flag": false
    }
    ```

    The single-seat shape persists the flag in the `band_seat_flags` table. Disabled seats remain disabled after room refresh and are excluded from bot fill. The legacy full-list seat shape is still accepted. Deleting the room also deletes its persistent seat flags.
  </Expandable>
</ExpandableGroup>

## Select a character and ready up

Each member selects a character independently, then changes their readiness state before the host starts the match.

<Steps>
  <Step title="Choose your character" title-type="p">
    Call `POST /api/v1/band_member/character` with the room ID and `input_character`.

    The server records the selection and sets your member state to `select_character`.
  </Step>

  <Step title="Toggle your ready state" title-type="p">
    Call `POST /api/v1/band_member/ready` with `ready: true` when you are ready to play. Send `ready: false` to return to the normal state.
  </Step>

  <Step title="Check member states" title-type="p">
    Read the current room model or apply the `member_update` command from the mutation event. The server serializes these states as lowercase strings:

    - `normal`
    - `ready`
    - `offline`
    - `leave`
    - `select_character`
    - `select_arena`
    - `chat`
  </Step>
</Steps>

## Start the match

The host starts a standard custom match with `POST /api/v1/band_match/start`. When `worker.enabled` is `true`, the server automatically spawns a dedicated game worker, waits for it to signal readiness, and then publishes the game-start event. No manual host startup is required.

The match type for `/band_match/start` is `practice`. The related endpoint `/api/v1/band_match/start_practice_competitive` uses match type `competitive`.

<Steps>
  <Step title="Start matchmaking from the room" title-type="p">
    Send the start request as the host. The server validates that the room is startable, creates tickets for all room members against the same match allocation, and places them immediately.

    When `worker.enabled` is `true`, the server spawns a dedicated game worker via `MatchWorkerSupervisor.Spawn()`, assigning it an available UDP port from the configured range. If the worker fails to spawn, the server cancels the match and returns an error.
  </Step>

  <Step title="Worker readiness check" title-type="p">
    The HTTP match-start response completes immediately so the client can process the game-start event. The server then waits for the worker to signal readiness by watching the worker's log for a `RosterReady` marker, which indicates the worker has loaded the map, prepared the roster, and is ready to accept player connections.

    The `band_game_start` event is published to room members only after the worker reports readiness. This prevents clients from attempting to connect before the game server is ready.
  </Step>

  <Step title="Handle startup timeout" title-type="p">
    If the worker does not bind within the 180-second startup timeout, the server terminates the worker process, stops the match, and logs an error. The room returns to `lobby` state and the host can try starting the match again.

    <Callout kind="alert" collapsed="false">
      A startup timeout usually means the game executable failed to initialize. Check the worker log under `_work/logs/match-workers/` for errors, and verify that `worker.installDirectory` and `worker.processPath` point to a valid game installation.
    </Callout>
  </Step>

  <Step title="Process the game-start event" title-type="p">
    Once the worker is ready, the server publishes a `band_game_start` event to each connected room member. Each member receives that member's own ticket ID and player session details.

    Apply the event commands before connecting the client to gameplay. Do not assume that every member can reuse the host's ticket or session ID.
  </Step>
</Steps>

<Callout kind="tip" collapsed="false">
  Port reservation and collision detection are handled automatically. The supervisor reserves the UDP port before spawning, checks for OS-level port conflicts, and releases the reservation on spawn failure, worker termination, or unexpected process exit.
</Callout>

The ticket state model still includes:

```text
queued
searching
matching
placing
activating
completed
failed
cancelled
timedout
```

Custom matches skip the queue and search states in normal operation. Their tickets move directly to `completed` after placement.

## Poll the ticket and connect to the game

Use `GET /api/ticket/describe?ticketId=ticket_01` when you need to inspect a ticket. A successful response includes richer allocation and player data:

```json
{
  "ticketId": "ticket_01",
  "status": "completed",
  "statusReason": "placed",
  "ruleId": 106,
  "profile": "practice",
  "currentPlayer": 1,
  "maxPlayer": 6,
  "now": 1710000000,
  "ipAddress": "192.0.2.44",
  "dnsName": "game-worker.internal",
  "port": 30000,
  "securityKey": "sk_example_7f3a91c4e2bd",
  "matchId": "match_01HZX4K7M2",
  "playerSessionId": "session_01HZX4K7M2",
  "matchType": "practice",
  "region": "global",
  "errorMessage": "",
  "errorCode": 0
}
```

Unknown ticket IDs now return `status: failed` with `errorCode: 404` instead of an empty successful response.

The completed ticket and `band_game_start` event provide the connection information required to enter gameplay:

- IP address
- DNS name, when configured
- UDP port
- Security key
- Match ID
- Player session ID
- Map and mode information
- Rule ID, queue or match type, and region

The client uses the returned address and port to connect to the configured dedicated-server worker over UDP. The completed ticket can also include allocation properties such as the worker allocation ID, map ID, mode ID, rule ID, queue type, and region.

When `worker.enabled` is `true`, the server automatically spawns and supervises the dedicated worker process. The connection details in the completed ticket point to the auto-spawned worker's address and port.

## Connect to the out-game WebSocket

The out-game WebSocket requires both `user_uid` and `connectionToken` query parameters:

```text
/ws?user_uid=account_42&connectionToken=token_example_8d21
```

The server validates the supplied credentials against a live, non-expired, non-revoked session record. Unauthorized sockets receive HTTP `401`.

After authentication, the server publishes `BandUpdateEvent` messages for room mutations and `BandGameStartEvent` messages when the match starts. Connected room members receive their own game-start data, including their individual ticket ID and `playerSessionId`.

## Arena schedules and matchmaking tokens

Use `GET /api/v1/arena_schedule/list` to read the configured arena and mode schedule. The response groups entries into:

- `normals`
- `competitive`
- `competitives`
- `variety`
- `lab`
- `bot`

Use `POST /api/v1/arena_schedule/token/create` to create matchmaking tokens for arena-based matchmaking. The arena configuration in `server-config.json` controls available slots, map IDs, token lifetime, and the competitive season.

## Stop or leave a match

Use `POST /api/v1/band_match/stop` with the room ID and ticket ID to stop matchmaking. The server cancels the ticket, terminates any associated dedicated worker process, and returns the room to `lobby` when the match is still stoppable.

Use `POST /api/v1/band_room/leave` when a player leaves the room:

- The leaving player is removed from the room.
- If the account in `HostUid` leaves while members remain, the first remaining member becomes host.
- If the last member leaves, the server deletes the room and its persistent seat flags.
- The server reconciles bot fill after membership changes.

The lobby sweeper releases abandoned rooms after the configured idle timeout. The default idle timeout is `180` seconds, and room activity updates the room heartbeat.

## Current limitations

<Callout kind="alert" collapsed="false">
  The current custom-match implementation has these limitations:

  - Rooms do not support password protection.
  - Social, chat, and instant endpoints remain compatibility stubs and do not provide their complete product behavior.
  - Players can enter the arena, move, and fight bots in custom matches, but the complete battle-finish and rewards flow has not been fully verified end-to-end.
  - The out-game WebSocket delivers room updates and game-start events, but it does not replace the remaining Unity gameplay synchronization layer.
</Callout>

The server can create and manage ten-seat rooms, persist seat flags, reconcile bots, allocate per-member tickets, and publish per-member game-start events. Custom matches now enter a playable arena with working movement and bot combat. Match completion and reward persistence remain under verification.
